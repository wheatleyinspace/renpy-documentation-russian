Сохранение, загрузка и откат

В Ren'Py есть поддержка сохранения состояния игры, загрузки состояния игры и отката назад к предыдущему состоянию игры. Хотя откат реализован несколько иначе, его можно рассматривать как сохранение игры в начале каждой взаимодействующей с пользователем инструкции и загрузку сохранений при откате пользователя назад.

Примечание

Хотя обычно разработчики стремятся сохранять совместимость сохранений между выпусками, эта совместимость не гарантируется. Мы можем нарушить совместимость сохранений, если это даёт достаточно весомые преимущества.

Что сохраняется

Ren'Py пытается сохранить состояние игры. Оно включает как внутреннее состояние, так и состояние Python.

Внутреннее состояние состоит из всех аспектов Ren'Py, которые предназначены для изменения после запуска игры, и включает в себя:

  • Текущую инструкцию и все инструкции, к которым можно вернуться.

  • Изображения и отображаемые объекты, которые в данный момент показываются.

  • Отображаемые экраны и значения переменных внутри этих экранов.

  • Музыку, которую воспроизводит Ren'Py.

  • Список текстовых блоков режима NVL.

Состояние Python состоит из переменных в хранилище (store), которые изменились с момента начала игры, и всех объектов, доступных из этих переменных. Обратите внимание, что значение имеет именно изменение самих переменных — изменение полей внутри объектов не приведёт к тому, что эти объекты будут сохранены.

Переменные, заданные с помощью инструкции default, всегда сохраняются.

В этом примере:

define a = 1
define o = object()
default c = 17

label start:
    $ b = 1
    $ o.value = 42

сохранены будут только b и c. Переменная a не будет сохранена, так как она не изменялась после запуска игры. o не сохраняется, потому что она не изменялась: объект, на который она ссылается, изменился, но сама переменная — нет.

Что не сохраняется

Переменные Python, не изменившиеся после начала игры, сохранены не будут. Это может стать серьёзной проблемой, если не сохраняемая переменная и сохраняемая переменная ссылаются на один и тот же объект (являются псевдонимами/алиасами объекта). В этом примере:

init python:
    a = object()
    a.f = 1

label start:
    $ b = a
    $ b.f = 2

    "a.f=[a.f] b.f=[b.f]"

a и b являются псевдонимами одного объекта. Сохранение и загрузка могут нарушить эту связь, из-за чего a и b начнут ссылаться на разные объекты. Поскольку это может приводить к трудноуловимым ошибкам, лучше избегать связывания псевдонимами сохраняемых и несохраняемых переменных. (Напрямую такое встречается редко, но может возникнуть при совместном использовании несохраняемой переменной и сохраняемого поля.)

Есть ещё несколько категорий состояния, которые не сохраняются:

путь управления (control flow path)

Ren'Py сохраняет только текущую инструкцию и инструкцию, к которой необходимо вернуться. Он не запоминает, как управление туда попало. Что немаловажно, инструкции (включая присвоения переменных), добавленные в игру позднее, выполняться не будут.

сопоставления имён изображений с отображаемыми объектами

Поскольку это сопоставление не сохраняется, изображение может замениться новым при следующей загрузке игры. Это позволяет обновлять графические файлы по мере разработки и обновления игры.

переменные конфигурации, стили и свойства стилей

Переменные конфигурации и стили не сохраняются как часть игры. Следовательно, их следует изменять только в блоках init и не трогать после запуска игры.

Где Ren'Py сохраняет игру

Сохранения происходят в начале инструкции Ren'Py в самом внешнем контексте взаимодействия.

Здесь важно отметить, что сохранение происходит в начале инструкции. Если загрузка или откат происходят посреди инструкции с многократным взаимодействием, состоянием игры будет то, которое было активно на момент начала инструкции.

Это может быть проблемой для инструкций, определённых на Python. Например, в коде:

python:

    i = 0

    while i < 10:

        i += 1

        narrator("The count is now [i].")

если пользователь сохранится и загрузится в середине цикла, цикл начнётся заново. Использование скрипта Ren'Py — вместо чистого Python — для организации цикла позволяет избежать этой проблемы.:

$ i = 0

while i < 10:

    $ i += 1

    "The count is now [i]."

Что Ren'Py может сохранить

Ren'Py использует систему pickle языка Python для сохранения состояния игры. Этот модуль может сохранять:

  • Базовые типы данных, такие как True, False, None, int, str, float, complex, bytes и Unicode-строки.

  • Составные типы, такие как списки (list), кортежи (tuple), множества (set) и словари (dict).

  • Определённые разработчиком объекты, классы, функции, методы и связанные методы (bound methods). Чтобы сериализация (pickling) этих функций прошла успешно, они должны оставаться доступными под своими исходными именами.

  • Объекты Character, Displayable, Transform и Transition.

Что Ren'Py не может сохранить

Существуют определённые типы данных, которые невозможно сериализовать через pickle:

  • Объекты Render.

  • Объекты-итераторы.

  • Объекты-генераторы.

  • Задачи корутин и объекты future, например, созданные с помощью async и await.

  • Файлоподобные объекты.

  • Сетевые сокеты и объекты, содержащие их внутри себя.

  • Внутренние функции (inner functions) и лямбда-выражения (lambdas).

Этот список может быть не исчерпывающим.

Объекты, которые нельзя сериализовать, всё же можно использовать, при условии, что их использование ограничено пространствами имён, которые не сохраняются Ren'Py (такими как переменные init, пространства имён внутри функций или блоки python hide).

Например, использование файлового объекта в таком виде:

$ monika_file = open(config.gamedir + "/monika.chr", "w")
$ monika_file.write("Do not delete.
")

$ monika_file.close()

не сработает, так как переменная может быть сохранена между любыми из этих трёх инструкций Python. Помещение этого кода в блок python hide будет работать корректно:

python hide:

    monika_file = open(config.gamedir + "/monika.chr", "w")
    monika_file.write("Do not delete.
")

monika_file.close()

(Разумеется, использование инструкции Python with будет ещё более аккуратным):

python hide:

    with open(config.gamedir + "/monika.chr", "w") as monika_file:
        monika_file.write("Do not delete.

")

Корутины, созданные с использованием async, await или модуля asyncio, ведут себя аналогично. Если у вас есть:

init python:

    import asyncio

    async def sleep_func():
        await asyncio.sleep(1)
        await asyncio.sleep(1)

то код:

$ sleep_task = sleep_func()
$ asyncio.run(sleep_task)

вызовет ошибки, поскольку sleep_task не может быть сохранена. Но если она не присваивается переменной:

$ asyncio.run(sleep_func())

то всё выполнится без проблем.

Структура файла сохранения

Файлы сохранений Ren'Py (например, 1-1.save) представляют собой сжатые архивы, содержащие:

  • Состояние игры: Сериализованные объекты Python, представляющие состояние игры.

  • Метаданные: Словарь с полями, описывающими сохранение. Доступные поля зависят от способа доступа:

    • renpy.slot_json(): Возвращает словарь с полями _save_name, _renpy_version, _version, _game_runtime, _ctime и любыми пользовательскими полями, добавленными через config.save_json_callbacks.

    • FileJson(): Возвращает тот же словарь метаданных, что и renpy.slot_json(), когда параметр key равен None (по умолчанию), включая пользовательские поля. Когда указан key (например, "_save_name"), возвращается значение этого поля.

    • renpy.list_saved_games(): Возвращает кортеж, содержащий _save_name (как extra_info), mtime (как time) и _screenshot (как screenshot), но без других полей метаданных.

    Стандартные поля метаданных включают:

    • _save_name: Строка, задаваемая аргументом extra_info в renpy.save(), обычно глобальная переменная save_name (например, «Глава 1»). Если не задано — пустая строка.

    • _renpy_version: Версия Ren'Py, использованная для создания сохранения, в виде списка целых чисел (например, [8, 3, 7, 25031702] для Ren'Py 8.3.7.25031702).

    • _version: Версия игры, заданная config.version на момент сохранения (например, «1.0»).

    • _game_runtime: Количество секунд, в течение которых игра ожидала ввода пользователя, возвращаемое renpy.get_game_runtime() на момент сохранения.

    • _ctime: Временная метка UNIX (секунды с начала эпохи), когда сохранение было создано.

    • _screenshot: Отображаемый объект для снимка экрана сохранения, доступный через renpy.list_saved_games() или FileScreenshot().

Метаданные хранятся в формате JSON и поэтому ограничены значениями, которые могут быть представлены в JSON: строками, числами, списками и словарями. При использовании _save_name (через save_name или extra_info) специальные символы, такие как [] или {}, могут вызвать проблемы, если они будут напрямую интерпретированы парсером текста Ren'Py в интерфейсе сохранения/загрузки, приводя к ошибкам или неожиданному отображению. Используйте config.save_json_callbacks для безопасного хранения сложных метаданных или используйте substitute False при их выводе в виде Text.

Сохранения при ошибках (Traceback Saves)

По возможности Ren'Py создаёт сохранения при возникновении необработанного исключения, сохраняя как состояние игры, так и трассировку стека (traceback). Эти сохранения размещаются в слотах с именами от _tracesave-1 до _tracesave-10. В этих файлах трассировка сохраняется в метаданных файла и может быть извлечена следующим образом:

traceback = renpy.slot_json("_tracesave-1")["_traceback"]

Также можно использовать renpy.get_save_data(), чтобы получить переменные, которые игра использовала в момент создания сохранения при ошибке.

Функция renpy.get_save_data() позволяет извлечь данные для определённого слота сохранения без непосредственной загрузки сохранения. Это можно использовать вместе с сохранением при ошибке, чтобы получить данные игры, не загружаясь в состояние с ошибкой.

Функции и переменные сохранения

Существует одна переменная, используемая высокоуровневой системой сохранения: save_name.

Это строка, которая сохраняется вместе с каждым файлом сохранения. Её можно использовать для задания имени сохранению, помогая пользователям различать их.

Более детальную настройку данных для каждого сохранения можно выполнить с помощью системы дополнительных данных JSON, см. config.save_json_callbacks.

В экранных действиях определён ряд высокоуровневых действий и функций сохранения. Кроме того, доступны следующие низкоуровневые действия и функции сохранения и загрузки.

renpy.can_load(filename, test=False)

Возвращает True, если filename (например, '3-2' для страницы 3, слота 2) существует как слот сохранения, и False в противном случае.

renpy.copy_save(old, new)

Копирует сохранение из old в new. (Ничего не делает, если old не существует.)

renpy.get_save_data(filename)

Загружает данные игры из слота сохранения filename (например, '3-2' для страницы 3, слота 2) без фактического изменения состояния игры. Возвращает словарь, сопоставляющий имена переменных относительно хранилища по умолчанию со значениями этих переменных на момент сохранения.

renpy.list_slots(regexp=None)

Возвращает список непустых слотов сохранения. Если regexp задано, возвращаются только слоты, начинающиеся с regexp. Слоты отсортированы в лексикографическом (строковом) порядке.

Список полезных регулярных выражений см. в описании list_saved_games().

renpy.load(filename)

Загружает состояние игры из слота сохранения filename (например, '3-2' для страницы 3, слота 2). При успешной загрузке файла эта функция никогда не возвращает управление.

renpy.newest_slot(regexp=None)

Возвращает имя самого нового слота сохранения (слота сохранения с самым последним временем изменения) или None, если нет (соответствующих) сохранений.

Если regexp задано, возвращаются только слоты, начинающиеся с regexp.

Список полезных регулярных выражений см. в описании list_saved_games().

renpy.rename_save(old, new)

Переименовывает сохранение из old в new. (Ничего не делает, если old не существует.)

renpy.save(filename, extra_info='', *, extra_json=None)

Сохраняет игру в слот, определяемый filename.

filename

Строка, задающая имя слота сохранения. Несмотря на имя переменной, оно лишь приблизительно соотносится с именами файлов на диске (например, '3-2' для страницы 3, слота 2).

extra_info

Строка, сохраняемая в поле _save_name в метаданных файла сохранения. Её можно получить с помощью renpy.slot_json() (по ключу "_save_name"), FileJson() (с key=None или key="_save_name") или как поле extra_info в renpy.list_saved_games(). Обычно используется с глобальной переменной save_name (например, "Глава 1"). Если строка пуста, _save_name будет пустой строкой.

extra_json

Словарь дополнительных метаданных для сохранения в файле. Он объединяется со стандартными метаданными и метаданными из config.save_json_callbacks.

Пример::

$ save_name = "Глава 1" $ renpy.save("1-1", extra_info=save_name)

Для хранения дополнительных или сложных метаданных используйте config.save_json_callbacks, чтобы добавлять пользовательские поля в словарь метаданных.

Перед этой функцией следует вызвать renpy.take_screenshot().

renpy.slot_json(slotname)

Возвращает словарь, содержащий метаданные файла сохранения в slotname, включая _save_name, _renpy_version, _version, _game_runtime, _ctime и любые пользовательские поля, добавленные через config.save_json_callbacks на момент сохранения. Если слот пуст, возвращается None. Для экранных действий сохранения/загрузки функция FileJson() предоставляет подмножество этих полей (исключая пользовательские поля).

Пример:

def show_game_runtime(slot):
    metadata = renpy.slot_json(slot)
    name = metadata.get('_save_name', '')
    runtime = metadata.get('_game_runtime', 0)
    hours = int(runtime // 3600)
    minutes = int((runtime % 3600) // 60)
    seconds = int(runtime % 60)
    runtime_formatted = f"{hours:02d}:{minutes:02d}:{seconds:02d}"
    renpy.notify("Save Name: [name], Game Runtime: [runtime_formatted]")
renpy.slot_mtime(slotname)

Возвращает время изменения для слота slotname или None, если слот пуст.

renpy.slot_screenshot(slotname)

Возвращает отображаемый объект, который может использоваться в качестве снимка экрана для slotname, или None, если слот пуст.

renpy.take_screenshot()

Делает снимок экрана. Этот снимок экрана будет сохранён как часть сохраняемой игры.

renpy.unlink_save(filename)

Удаляет слот сохранения с указанным именем (например, '3-2' для страницы 3, слота 2).

Сохранение данных после загрузки

При загрузке игры состояние сбрасывается (с использованием системы отката, описанной ниже) до состояния, в котором игра находилась в момент начала выполнения текущей инструкции.

В некоторых случаях это может быть нежелательно. Например, когда экран позволяет редактировать значение, мы можем захотеть сохранить это значение при загрузке игры. При вызове renpy.retain_after_load данные не будут сбрасываться, если игра сохранена и загружена до окончания следующего взаимодействия с контрольной точкой.

Обратите внимание, что хотя данные не изменяются, управление возвращается в начало текущей инструкции. Эта инструкция выполнится снова, уже с новыми данными, находящимися на месте в начале инструкции.

Например:

screen edit_value:
    hbox:
        text "[value]"
        textbutton "+" action SetVariable("value", value + 1)
        textbutton "-" action SetVariable("value", value - 1)
        textbutton "+" action Return(True)

label start:
    $ value = 0
    $ renpy.retain_after_load()
    call screen edit_value
renpy.retain_after_load()

Указывает сохранять данные, изменённые между текущей инструкцией и инструкцией, содержащей следующую контрольную точку (чекпоинт), при выполнении загрузки.

Откат (Rollback)

Откат позволяет пользователю вернуть игру в более раннее состояние точно так же, как системы отмены/повтора (undo/redo), доступные в большинстве современных приложений. Хотя система сама заботится о сохранении визуальных элементов и игровых переменных во время событий отката, есть ряд аспектов, которые следует учитывать при создании игры.

Какие данные откатываются?

Откат затрагивает переменные, которые были изменены после фазы инициализации (init), и объекты откатываемых типов, доступные из этих переменных. Вкратце: списки, словари и множества, созданные в скриптах Ren'Py, являются откатываемыми, так же как и экземпляры классов, определённых в скриптах Ren'Py. Данные, созданные внутри чистого Python или внутри самого ядра Ren'Py, обычно не откатываются.

Более подробно: внутри хранилищ (stores), в которых выполняется Python, встроенный в скрипты Ren'Py, типы object, list, dict и set были заменены эквивалентными типами, поддерживающими откат. Объекты, наследующие от этих типов, также поддерживают откат. Тип renpy.Displayable наследует от откатываемого типа object.

Чтобы сделать использование откатываемых объектов более удобным, Ren'Py модифицирует код Python внутри файлов скрипта Ren'Py следующим образом:

  • Литералы списков, словарей и множеств автоматически преобразуются в откатываемые эквиваленты.

  • Генераторы списков, словарей и множеств (comprehensions) также автоматически преобразуются в откатываемый эквивалент.

  • Другие синтаксические конструкции Python, такие как расширенная распаковка, способные создавать списки, словари или множества, преобразуют результат в откатываемый эквивалент. Однако из соображений производительности параметры функций и методов со звёздочками **kwargs (создающие словари дополнительных именованных аргументов) не преобразуются в откатываемые объекты.

  • Классы, которые не наследуются ни от каких других типов, автоматически наследуются от откатываемого object.

Кроме того:

  • Методы и операторы откатываемых типов были изменены так, чтобы возвращать откатываемые объекты, когда результатом операции является список, словарь или множество.

  • Встроенные функции, возвращающие списки, словари и множества, возвращают откатываемый эквивалент.

Вызов внешнего кода Python обычно не приводит к созданию откатываемого объекта. Вот некоторые случаи, когда вы получите объект, который может не участвовать в откате:

  • Вызов методов встроенных типов, таких как метод str.split.

  • Когда объект создаётся в импортированном модуле Python, а затем возвращается в Ren'Py. (Например, экземпляр collections.defaultdict не будет участвовать в откате.)

  • Объекты, возвращаемые из API Ren'Py, если в документации не указано иное.

Если такие данные должны участвовать в откате, имеет смысл преобразовать их к типу, который его поддерживает. Например:

# Вызов list внутри Python-в-Ren'Py преобразует неоткатываемый список
# в откатываемый.
$ attrs = list(renpy.get_attributes("eileen"))

Поддержка отката назад и отката вперёд

Большинство инструкций Ren'Py автоматически поддерживают откат назад и откат вперёд. Если вы вызываете ui.interact() напрямую, вам потребуется добавить поддержку отката назад и отката вперёд самостоятельно. Это можно сделать с помощью следующей структуры:

# Это None, если мы не откатываемся назад, или значение, переданное
# в checkpoint в прошлый раз, если выполняется откат вперёд.
roll_forward = renpy.roll_forward_info()

# Здесь настраивается экран...

# Взаимодействие с пользователем.
rv = ui.interact(roll_forward=roll_forward)

# Сохранение результата взаимодействия.
renpy.checkpoint(rv)

Важно, чтобы ваша игра не взаимодействовала с пользователем после вызова renpy.checkpoint. (Иначе пользователь может оказаться не в состоянии выполнить откат назад.)

renpy.can_rollback()

Возвращает True, если возможен откат назад.

renpy.checkpoint(data=None, *, hard=True)

Делает текущую инструкцию контрольной точкой (чекпоинтом), к которой пользователь может откатиться. После вызова этой функции в текущей инструкции больше не должно происходить взаимодействия с пользователем.

Это также очищает текущий снимок экрана, используемый для сохранений игры.

data

Эти данные возвращаются функцией renpy.roll_forward_info(), когда в игре выполняется откат вперёд.

hard

Если True, это жесткая контрольная точка, на которой откат остановится. Если False, это мягкая контрольная точка, которая не останавливает откат.

renpy.get_identifier_checkpoints(identifier)

Принимая identifier (идентификатор отката) из объекта HistoryEntry, возвращает количество контрольных точек, которое необходимо передать в renpy.rollback(), чтобы достичь этого идентификатора. Возвращает None, если идентификатор не найден в истории отката.

renpy.in_rollback()

Возвращает True, если игра сейчас находится в состоянии отката.

renpy.roll_forward_info()

В состоянии отката возвращает данные, переданные в renpy.checkpoint() при последнем выполнении этой инструкции. Вне отката возвращает None.

renpy.rollback(force=False, checkpoints=1, defer=False, greedy=True, label=None, abnormal=True)

Откатывает состояние игры назад к последней контрольной точке.

force

Если True, откат будет выполнен при любых обстоятельствах. В противном случае откат произойдёт только в том случае, если откат включён в хранилище, контексте и конфигурации.

checkpoints

Ren'Py выполнит откат назад через указанное число вызовов renpy.checkpoint. Игра откатится назад настолько далеко, насколько это возможно с учётом данного условия.

defer

Если True, вызов будет отложен до тех пор, пока управление не вернётся в главный контекст.

greedy

Если True, откат завершится сразу после предыдущей контрольной точки. Если False, откат завершится непосредственно перед текущей контрольной точкой.

label

Если не None, метка, которая будет вызвана по завершении отката.

abnormal

Если True (по умолчанию), скрипт, выполняемый после перехода, запускается в особом режиме, пропускающем переходы, которые иначе бы произошли. Этот режим завершается при начале взаимодействия.

renpy.suspend_rollback(flag)

Откат будет пропускать участки игры, в которых откат был приостановлен.

flag

Когда flag равен True, откат приостанавливается. Когда False — откат возобновляется.

Блокировка отката

Предупреждение

Блокировка отката недружелюбна по отношению к пользователю. Если пользователь по ошибке кликнет на нежелательный вариант ответа, он или она не сможет исправить свою ошибку. Поскольку откат эквивалентен сохранению и загрузке, ваши пользователи будут вынуждены сохраняться гораздо чаще, что разрушает погружение в игру.

Откат можно отключить частично или полностью. Если откат не нужен вовсе, его можно просто выключить через опцию config.rollback_enabled.

Более распространена частичная блокировка отката. Этого можно достичь с помощью функции renpy.block_rollback(). При её вызове Ren'Py получит команду не откатываться назад дальше этой точки. Например:

label final_answer:
    "Is that your final answer?"

menu:
    "Yes":
        jump no_return
    "No":
        "We have ways of making you talk."
        "You should contemplate them."
        "I'll ask you one more time..."
        jump final_answer

label no_return:
    $ renpy.block_rollback()

    "So be it. There's no turning back now."

При достижении метки no_return Ren'Py не позволит выполнить откат назад к меню.

Фиксация отката (Fixing Rollback)

Фиксация отката представляет собой промежуточный вариант между свободным откатом и полной его блокировкой. Откат разрешён, но пользователь не может изменить свои решения. Фиксация отката осуществляется с помощью функции renpy.fix_rollback(), как показано в следующем примере:

label final_answer:
    "Is that your final answer?"
menu:
    "Yes":
        jump no_return
    "No":
        "We have ways of making you talk."
        "You should contemplate them."
        "I'll ask you one more time..."
        jump final_answer

label no_return:
    $ renpy.fix_rollback()

    "So be it. There's no turning back now."

Теперь после вызова функции fix_rollback пользователь по-прежнему сможет откатиться назад к меню. Однако выбрать другой вариант ответа будет невозможно.

При проектировании игры с использованием fix_rollback следует учитывать некоторые нюансы. Ren'Py автоматически позаботится о блокировке любых данных, переданных в checkpoint(). Однако из-за гибкой природы Ren'Py можно написать скрипты в обход этого механизма, изменяющие состояние так, что это приведёт к непредсказуемым результатам. В частности, call screen плохо работает с фиксированным откатом. Разработчик сам должен позаботиться о блокировке отката в проблемных местах.

Встроенные средства взаимодействия с пользователем для меню, renpy.input() и renpy.imagemap(), спроектированы так, чтобы полноценно работать с fix_rollback.

Стилизация фиксированного отката

Поскольку fix_rollback изменяет поведение меню и imagemap, рекомендуется отражать это в их внешнем виде. Для этого важно понимать, как изменяются состояния виджетов кнопок меню. Существует два режима, которые можно выбрать с помощью параметра config.fix_rollback_without_choice.

По умолчанию выбранный вариант получает состояние «selected», тем самым активируя свойства стиля с префиксом «selected_». Все остальные кнопки становятся нечувствительными и отображаются свойствами с префиксом «insensitive_». Фактически в меню остаётся только один вариант.

Когда параметру config.fix_rollback_without_choice присвоено значение False, все кнопки становятся нечувствительными. Это означает, что выбранный вариант будет использовать префикс «selected_insensitive_» для свойств стиля, тогда как другие кнопки будут использовать свойства с префиксом «insensitive_».

Фиксированный откат и пользовательские экраны

Для упрощения создания пользовательских экранов предусмотрены два экранных действия, помогающие в наиболее распространённых сценариях. Действие ui.ChoiceReturn() возвращает значение при нажатии на кнопку, к которой оно привязано. Действие ui.ChoiceJump() можно использовать для перехода на метку скрипта. Однако это действие работает должным образом только тогда, когда экран вызван с помощью инструкции call screen.

Примеры:

screen demo_imagemap():
    roll_forward True

    imagemap:
        ground "imagemap_ground.jpg"
        hover "imagemap_hover.jpg"
        selected_idle "imagemap_selected_idle.jpg"
        selected_hover "imagemap_hover.jpg"

        hotspot (8, 200, 78, 78) action ui.ChoiceJump("swimming", "go_swimming", block_all=False)
        hotspot (204, 50, 78, 78) action ui.ChoiceJump("science", "go_science_club", block_all=False)
        hotspot (452, 79, 78, 78) action ui.ChoiceJump("art", "go_art_lessons", block_all=False)
        hotspot (602, 316, 78, 78) action ui.ChoiceJump("home", "go_home", block_all=False)

screen rps():
    roll_forward True

    hbox:
        imagebutton:
            idle "rock.png"
            hover "rock_hover.png"
            selected_insensitive "rock_hover.png"
            action ui.ChoiceReturn("rock", "Rock", block_all=True)
        imagebutton:
            idle "paper.png"
            hover "paper_hover.png"
            selected_insensitive "paper_hover.png"
            action ui.ChoiceReturn("paper", "Paper", block_all=True)
        imagebutton:
            idle "scissors.png"
            hover "scissors_hover.png"
            selected_insensitive "scissors_hover.png"
            action ui.ChoiceReturn("scissors", "Scissors", block_all=True)

        if renpy.in_fixed_rollback():
            textbutton "Advance":
                action Return(renpy.roll_forward_info())
                # требуется из-за block_all=True во всех остальных кнопках

label dough:
    call screen rps
    $ chosen = _return
    $ renpy.fix_rollback()
    m "[chosen]!"

При написании пользовательских функций на Python, которые должны корректно взаимодействовать с системой fix_rollback, полезно знать несколько простых правил. Во-первых, функцию renpy.in_fixed_rollback() можно использовать для проверки того, находится ли игра в данный момент в состоянии фиксированного отката. Во-вторых, в состоянии фиксированного отката функция ui.interact() всегда будет возвращать переданные данные roll_forward, независимо от того, какое действие было совершено. Это фактически означает, что при использовании функций ui.interact() и renpy.checkpoint() большая часть работы уже сделана.

Функции блокировки и фиксации отката

renpy.block_rollback()

Предотвращает откат игры к состоянию до текущей инструкции.

renpy.fix_rollback()

Предотвращает изменение пользователем решений, принятых до текущей инструкции.

renpy.in_fixed_rollback()

Возвращает True, если в данный момент происходит откат и текущий контекст предшествует выполненной инструкции renpy.fix_rollback().

ui.ChoiceJump(label, value, location=None, block_all=None, sensitive=True, args=None, kwargs=None)

Действие выбора в меню, возвращающее value и управляющее состоянием кнопки в соответствии с фиксированным откатом. (Описание поведения см. в параметре block_all.)

label

Текст метки кнопки. Для imagebutton и hotspot может быть любым. Эта метка используется как уникальный идентификатор варианта в пределах текущего экрана. Вместе с location используется для сохранения факта выбора этого варианта.

value

Метка перехода (куда совершить переход).

location

Уникальный идентификатор местоположения для текущего экрана выборов.

block_all

Если False, кнопке присваивается роль selected, если это был сделанный выбор, и insensitive, если выбор не был выбран.

Если True, кнопка всегда нечувствительна (insensitive) во время фиксированного отката.

Если None, значение берётся из переменной config.fix_rollback_without_choice.

Если значение True задано для всех элементов экрана, он станет некликабельным (откат вперёд по-прежнему будет работать).

ui.ChoiceReturn(label, value, location=None, block_all=None, sensitive=True, args=None, kwargs=None)

Действие выбора в меню, возвращающее value и управляющее состоянием кнопки в соответствии с фиксированным откатом. (Описание поведения см. в параметре block_all.)

label

Текст метки кнопки. Для imagebutton и hotspot может быть любым. Эта метка используется как уникальный идентификатор варианта в пределах текущего экрана. Вместе с location используется для сохранения факта выбора этого варианта.

value

Значение, возвращаемое при выборе этого варианта.

location

Уникальный идентификатор местоположения для текущего экрана выборов.

block_all

Если False, кнопке присваивается роль selected, если это был сделанный выбор, и insensitive, если выбор не был выбран.

Если True, кнопка всегда нечувствительна (insensitive) во время фиксированного отката.

Если None, значение берётся из переменной config.fix_rollback_without_choice.

Если значение True задано для всех элементов экрана, он станет некликабельным (откат вперёд по-прежнему будет работать).

NoRollback

class NoRollback

Экземпляры этого класса и классов, наследующихся от него, не участвуют в откате. Объекты, доступные через экземпляр класса NoRollback, участвуют в откате только в том случае, если они доступны через другие пути.

class SlottedNoRollback

Экземпляры классов, наследующихся от этого класса, не участвуют в откате. Разница между этим классом и NoRollback заключается в том, что у этого класса нет связанного словаря, поэтому его можно использовать с __slots__ для снижения потребления памяти.

Объекты, доступные через экземпляр класса NoRollback, участвуют в откате только в том случае, если они доступны через другие пути.

Например:

init python:

    class MyClass(NoRollback):
        def __init__(self):
            self.value = 0

label start:
    $ o = MyClass()

    "Welcome!"

    $ o.value += 1

    "o.value is [o.value]. It will increase each time you rollback and then click ahead."

Классы, поддерживающие откат

Следующие классы предназначены для облегчения использования отката в вашей игре. Они могут оказаться полезными в ряде ситуаций.

class MultiRevertable

MultiRevertable — это класс-примесь (mixin), позволяющий объекту наследоваться более чем от одного типа откатываемых объектов. Чтобы использовать его, выполните наследование от MultiRevertable, а затем от откатываемых классов, от которых хотите унаследоваться.

Например:

class MyDict(MultiRevertable, dict, object):
    pass

создаст класс, который будет откатывать как содержимое своего словаря (dict), так и поля объекта (object).

class defaultdict(default_factory, /, *args, **kwargs)

Это откатываемая версия collections.defaultdict. Принимает функцию-фабрику. При обращении к несуществующему ключу вызывается функция default_factory с этим ключом в качестве аргумента, и возвращается полученный результат.

Хотя атрибут default_factory присутствует в этом объекте, он не участвует в откате, и поэтому не должен изменяться.
